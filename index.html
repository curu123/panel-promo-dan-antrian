Dari pesan error di aplikasi terlihat jelas: update or delete on table "inventory" violates foreign key constraint "service_order_items_inventory_id_fkey" Key is still referenced from table "service_order_items" Artinya record Oppo a15/A16 di inventory pernah dipakai pada data service/order. PostgreSQL sengaja menolak penghapusan supaya riwayat service tidak rusak. Solusi paling aman untuk RK CELL: jangan benar-benar DELETE barang yang pernah dipakai transaksi. Lebih baik buat sistem nonaktif/arsip. Tambahkan kolom: alter table public.inventory add column if not exists is_active boolean not null default true; Lalu saat pengguna menekan Hapus Barang, aplikasi sebenarnya menjalankan: update public.inventory set is_active = false, updated_at = now() where id = 'ID_BARANG'; Kemudian daftar stok aplikasi hanya membaca: select * from public.inventory where is_active = true; Barang hilang dari daftar stok aktif, tetapi riwayat service_order_items tetap aman. Untuk monitor stok yang sedang kita buat, ubah RPC/view supaya hanya menampilkan barang aktif: ... from public.inventory i where coalesce(i.is_active, true) = true order by i.name asc; Kalau suatu saat ingin mengembalikan barang: update public.inventory set is_active = true where id = 'ID_BARANG'; Saya tidak menyarankan ON DELETE CASCADE, karena itu bisa ikut menghapus detail item pada riwayat service ketika barang dihapus. Untuk sistem service seperti RK CELL, metode arsip/nonaktif jauh lebih aman. Error ini justru membantu—database Anda punya pengaman tambahan chk_source_internal. Artinya untuk baris dengan: source = internal database mewajibkan inventory_id tetap terisi. Jadi ketika FK mencoba mengubah inventory_id menjadi NULL, check constraint menolaknya. Karena SQL sebelumnya memakai BEGIN ... COMMIT, saat terjadi error transaksi tersebut rollback, jadi perubahan sebelumnya tidak setengah jalan. Sekarang jangan jalankan SQL hapus lain dulu. Kita perlu melihat persis aturan chk_source_internal. Jalankan ini: select conname, pg_get_constraintdef(oid) as definition from pg_constraint where conrelid = 'public.service_order_items'::regclass and conname = 'chk_source_internal'; Kemungkinan hasilnya kurang lebih seperti: CHECK ( (source = 'internal' AND inventory_id IS NOT NULL) OR (source = 'external' ...) ) Setelah Anda kirim hasilnya, saya akan buat SQL final yang aman. Kemungkinan solusi akhirnya adalah mengizinkan riwayat lama seperti ini: source = internal inventory_id = NULL external_item_name = "Vivo Y17/y12/y15" Jadi nama barang tetap tersimpan sebagai snapshot, tetapi barang asli di inventory boleh benar-benar dihapus. Kita perlu menyesuaikan chk_source_internal dengan aturan yang tepat, bukan menghapus constraint begitu saja. Nah, sekarang penyebabnya sudah jelas. Constraint lama memang mewajibkan setiap source = 'internal' memiliki inventory_id. Kita ubah aturannya sedikit: item internal boleh kehilangan inventory_id asal nama barang sudah disimpan sebagai snapshot di external_item_name. Jalankan SQL final berikut di Supabase.
